# BE-035 미구현 사유 및 대체 구조

## 목적

이 문서는 `BE-035 2차 인증 설정 API`를 현재 시점에서 별도 구현하지 않는 이유와, 이를 어떤 구조로 대체하는지 설명하기 위한 문서다.

## 결론

현재 프로젝트에서는 `BE-035 2차 인증 설정 API`를 별도로 구현하지 않아도 된다.

그 이유는 현재 구조에서 2차 인증 방식이 사용자 사전 설정값이 아니라, 결제 시점의 `RBA` 판정 결과로 결정되기 때문이다.

즉 현재 대체 구조는 다음과 같다.

- `PIN`은 사용자가 직접 설정한다
- `전화번호`는 회원 정보에 이미 저장되어 있다
- `RBA`가 결제 상황에 따라 어떤 2차 인증이 필요한지 결정한다
- 결제 흐름에서 해당 방식으로 바로 추가 인증을 수행한다

## 왜 미구현해도 되는가

### 1. 인증 방식 결정 로직이 이미 존재한다

현재 시스템은 `RBA`를 통해 아래와 같은 인증 레벨을 계산할 수 있다.

- `FACE_ONLY`
- `FACE_PHONE`
- `FACE_PIN`
- `FACE_SIGNATURE`
- `BLOCKED`

즉 추가 인증이 필요한지, 필요하다면 어떤 종류가 필요한지는 이미 `RBA` 결과로 표현 가능하다.

### 2. 사용자 인증 수단도 이미 준비되어 있다

현재 구조에서 2차 인증에 필요한 수단은 이미 별도 설정 API 없이도 확보 가능하다.

- `PHONE`
  - 회원 정보에 전화번호가 저장되어 있음
- `PIN`
  - `BE-034`에서 PIN 설정/변경 API 구현
- `SIGNATURE`
  - 필요 시 결제 단계에서 전자서명 여부 확인 가능

즉 “추가 인증 수단을 무엇으로 쓸 수 있는가” 자체는 별도 설정 API 없이도 이미 관리 가능하다.

### 3. 사용자 선택형 설정 요구가 아직 없다

`BE-035`가 꼭 필요한 경우는 보통 아래와 같다.

- 사용자가 `PIN`과 `PHONE` 중 선호 인증 수단을 직접 선택해야 하는 경우
- 특정 인증 수단을 활성화/비활성화해야 하는 경우
- 사용자별로 기본 2차 인증 방식을 커스터마이징해야 하는 경우

하지만 현재 프로젝트에서는 이런 요구가 확정되어 있지 않다.

따라서 지금 시점에서 `BE-035`를 구현하면, 실제 필요성보다 구조 복잡도만 늘어날 수 있다.

## 현재 대체 구조

현재는 별도의 `2차 인증 설정 API` 대신 아래 구조로 동작한다.

`결제 요청 -> 얼굴 매칭 -> RBA 판정 -> 필요한 2차 인증 방식 결정 -> 해당 인증 수행`

### 1. PIN 설정

- `BE-034`에서 사용자가 6자리 PIN을 설정/변경

### 2. 전화번호 인증 정보

- 회원가입 시 저장된 전화번호 사용

### 3. RBA 판정

- 얼굴 유사도
- 거래 금액
- 정책 엔진

위 정보를 바탕으로 `authLevel` 결정

예:

- `FACE_ONLY`
- `FACE_PHONE`
- `FACE_PIN`
- `FACE_SIGNATURE`

### 4. 결제 단계에서 실제 추가 인증 수행

- `authLevel=FACE_PHONE`
  - 전화번호 2차 인증 수행
- `authLevel=FACE_PIN`
  - PIN 입력 및 검증 수행
- `authLevel=FACE_SIGNATURE`
  - 전자서명 수행

즉 현재 대체 구조는 “사용자 설정 기반”이 아니라 “RBA 결과 기반”이다.

## 장점

- API 수를 불필요하게 늘리지 않는다
- 현재 요구사항에 비해 과도한 사용자 설정 로직을 만들지 않는다
- `RBA`가 인증 방식을 일관되게 결정하므로 흐름이 단순하다
- `PIN`, `PHONE`, `SIGNATURE`를 각 단계에서 독립적으로 구현 가능하다

## 한계

- 사용자가 직접 “내 기본 2차 인증 수단은 PIN” 같은 선호 설정을 저장할 수 없다
- 인증 방식 선택권이 사용자보다 시스템 정책에 더 많이 의존한다

하지만 현재 프로젝트 단계에서는 이 한계보다 구조 단순성과 구현 속도의 이점이 더 크다.

## 최종 판단

현재 프로젝트에서 `BE-035`는 아래 이유로 미구현해도 된다.

- 이미 `RBA` 결과로 필요한 2차 인증 방식 결정 가능
- 전화번호와 PIN 같은 인증 수단이 별도로 준비 가능
- 사용자 선택형 2차 인증 설정 요구가 아직 핵심 기능이 아님

따라서 현재 대체 구조는 다음 한 줄로 정리할 수 있다.

`2차 인증 설정 API 대신, RBA가 결정한 인증 방식에 따라 결제 단계에서 PHONE/PIN/SIGNATURE 인증을 수행한다.`
