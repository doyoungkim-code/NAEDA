# BE-033 EC2 배포 후 검증 시나리오

## 목적

이 문서는 `EC2 Linux`에 `BE`와 `AI(PaddleOCR)`를 배포한 뒤 `BE-033 신분증 OCR 검증 API`가 실제로 완료되었는지 확인하기 위한 검증 시나리오를 정리한 문서다.

핵심은 아래 3가지를 확인하는 것이다.

- `AI`가 Linux 환경에서 `PaddleOCR` 실제 추론에 성공하는가
- `BE -> AI` 연동이 정상 동작하는가
- 최종 확인 API까지 포함한 사용자 흐름이 정상 완료되는가

## 1. 검증 대상

- `AI`
  - `POST /internal/v1/ocr/id-card/extract`
- `BE`
  - `POST /api/v1/identity/id-card/extract`
  - `POST /api/v1/identity/id-card/confirm`

## 2. 사전 조건

- [ ] EC2에서 `AI`가 `RESIDENT_OCR_PROVIDER=paddleocr`로 실행 중
- [ ] `BE`가 해당 `AI`를 내부 주소로 호출 중
- [ ] `BE`와 `AI`의 서비스 토큰이 일치
- [ ] 테스트용 주민등록증 또는 운전면허증 샘플 이미지 준비
- [ ] 테스트용 사용자 계정이 존재
- [ ] 해당 사용자의 `username`, `resident_no` 값이 확인 가능

## 3. 시나리오 1: AI 헬스체크 확인

### 목적

`AI` 컨테이너가 정상 기동했는지 확인한다.

### 절차

1. `AI` health endpoint 호출
2. HTTP `200` 확인

### 기대 결과

- `AI`가 응답 가능 상태다.
- 컨테이너 기동 직후 모델 다운로드로 인한 비정상 종료가 없다.

## 4. 시나리오 2: AI 내부 OCR 직접 검증

### 목적

`PaddleOCR`가 Linux에서 실제 추론 가능한지 직접 확인한다.

### 절차

1. 테스트 이미지를 `AI /internal/v1/ocr/id-card/extract`로 전송
2. 응답 코드와 응답 본문 확인

### 기대 결과

- HTTP `200`
- `provider=paddleocr`
- `documentMatched=true`
- `name` 추출 성공
- `residentFront6` 추출 성공
- `residentBackFirst1` 추출 성공

### 실패 시 판정

- `503 OCR_UNAVAILABLE`
  - Linux 런타임 또는 Paddle 초기화/추론 문제 가능성
- `400 OCR_EXTRACTION_FAILED`
  - 이미지 품질 또는 후처리 규칙 문제 가능성
- 타임아웃
  - 모델 초기화 지연 또는 서버 자원 부족 가능성

## 5. 시나리오 3: BE OCR 추출 API 검증

### 목적

`BE -> AI` 연동이 정상인지 확인한다.

### 절차

1. 인증 가능한 상태에서 `BE /api/v1/identity/id-card/extract` 호출
2. 이미지 업로드
3. 응답 확인

### 기대 결과

- HTTP `200`
- 응답 필드:
  - `documentType`
  - `documentMatched`
  - `name`
  - `residentFront6`
  - `residentBackFirst1`
  - `provider`
  - `confidence`
- `provider=paddleocr`

### 추가 확인

- `BE` 로그에 `AI` 호출 오류가 없어야 한다.
- `AI` 응답 지연이 과도하지 않아야 한다.

## 6. 시나리오 4: 최종 확인 API 성공 케이스

### 목적

OCR 추출값이 실제 사용자 정보와 일치할 때 다음 단계로 정상 진행되는지 확인한다.

### 절차

1. `extract` 결과를 확인한다.
2. 추출된 `name`, `residentFront6`, `residentBackFirst1` 값을 그대로 사용한다.
3. `BE /api/v1/identity/id-card/confirm` 호출

### 기대 결과

- HTTP `200`
- `verified=true`
- `nameMatched=true`
- `residentNoMatched=true`
- `nextAction=CONTINUE_FACEPAY_REGISTRATION`

## 7. 시나리오 5: 최종 확인 API 실패 케이스

### 목적

사용자 수정값이 회원 정보와 다를 때 재확인 흐름이 정상 동작하는지 확인한다.

### 절차

1. `confirm` 요청에서 이름 또는 주민번호 일부를 일부러 틀리게 보낸다.

### 기대 결과

- HTTP `200`
- `verified=false`
- `nameMatched` 또는 `residentNoMatched` 중 하나 이상 `false`
- `nextAction=RETRY_CONFIRM`

## 8. 시나리오 6: 문서 종류 검증

### 목적

지원 문서만 허용되는지 확인한다.

### 절차

1. 주민등록증 이미지 테스트
2. 운전면허증 이미지 테스트
3. 지원하지 않는 이미지 또는 문서 테스트

### 기대 결과

- 주민등록증: 정상 추출
- 운전면허증: 정상 추출
- 비지원 문서:
  - `documentMatched=false` 또는
  - `400 OCR_EXTRACTION_FAILED` / 비지원 문서 오류 처리

## 9. 시나리오 7: 예외 케이스 검증

### 목적

실서비스에서 자주 발생할 수 있는 입력 오류를 확인한다.

### 케이스

#### 빈 파일 업로드

기대 결과:

- HTTP `400`
- `EMPTY_IMAGE` 또는 동등한 입력 오류

#### 잘못된 이미지 형식

기대 결과:

- HTTP `400`
- `INVALID_IMAGE` 또는 `UNSUPPORTED_IMAGE_TYPE`

#### 용량 초과 이미지

기대 결과:

- HTTP `400`
- `IMAGE_TOO_LARGE`

#### AI 서비스 토큰 불일치

기대 결과:

- `BE -> AI` 호출 실패
- 인증 오류 또는 `OCR_UNAVAILABLE` 계열 처리

## 10. 시나리오 8: 성능 확인

### 목적

기본 응답성이 허용 범위인지 확인한다.

### 절차

1. 같은 종류의 샘플 이미지로 3회 이상 반복 호출
2. 응답 시간 측정

### 기대 결과

- 첫 요청:
  - 모델 초기화로 다소 느릴 수 있음
- 이후 요청:
  - 타임아웃 이내 안정 응답

### 점검 포인트

- 첫 요청이 지나치게 느리면 warm-up 전략 검토
- 반복 호출에서 지연이 누적되면 EC2 스펙 또는 동시성 설정 검토

## 11. 시나리오 9: 로그 및 운영 확인

### 목적

운영 시 문제 추적이 가능한 상태인지 확인한다.

### 절차

1. 성공 호출 1회 수행
2. 실패 호출 1회 수행
3. `BE`, `AI` 로그 확인

### 기대 결과

- `BE` 로그:
  - AI 호출 성공/실패 여부 확인 가능
- `AI` 로그:
  - provider
  - OCR 처리 시간
  - 실패 코드 확인 가능
- 주민번호 전체나 원본 이미지가 로그에 남지 않는다

## 12. 최종 완료 판정

아래 조건을 모두 만족하면 `BE-033`은 완료로 판단한다.

- [ ] `AI`가 EC2 Linux에서 `PaddleOCR` 실제 추론에 성공
- [ ] `BE /extract`가 OCR 결과를 정상 반환
- [ ] `BE /confirm`이 성공/실패 케이스 모두 기대대로 동작
- [ ] 입력 오류와 장애 케이스의 예외 처리가 정상
- [ ] 응답 시간과 로그 상태가 운영 가능한 수준

## 13. 최종 메모

현재 단계에서 `BE-033`의 마지막 리스크는 코드 구현보다 `EC2 Linux`에서의 `PaddleOCR` 실추론 안정성이다.

따라서 배포 후에는 먼저 `AI 내부 OCR 직접 검증`부터 수행하고, 그 다음 `BE extract`, 마지막으로 `confirm` 순서로 검증하는 것이 가장 효율적이다.
