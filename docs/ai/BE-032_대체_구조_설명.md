# BE-032 대체 구조 설명

## 목적

이 문서는 `BE-032 페이스페이 등록 오케스트레이션 API`를 별도 구현하지 않고, 현재 프로젝트에서 어떤 구조로 이를 대체하는지 설명하기 위한 문서다.

결론부터 말하면, 현재 프로젝트는 `오케스트레이션 API` 대신 `FE 주도 등록 플로우 + BE 단계별 처리 API` 구조로 충분히 요구사항을 충족한다.

## 결론

현재는 별도의 `BE 오케스트레이션 API`를 만들지 않는다.

대신 아래 구조로 등록 절차를 처리한다.

- `FE`
  - 등록 절차를 직접 제어
  - 촬영 순서 안내
  - 포즈별 촬영 진행
  - 민증 정보 확인 화면 제어
  - 실패 시 재촬영 유도
- `BE`
  - 단계별 검증 및 저장 API 제공
  - OCR 확인
  - 얼굴 방향 검증
  - 얼굴 임베딩 저장
- `AI`
  - OCR, headpose, embedding 추론 담당

즉 현재 대체 구조는 아래와 같다.

`FE -> BE(단계별 API) -> AI`

## 왜 오케스트레이션 API를 만들지 않는가

현재 프론트는 이미 아래 역할을 수행하고 있다.

- `정면 3장`, `좌`, `우` 등 촬영 순서 안내
- 어떤 포즈를 지금 촬영하는지 상태 관리
- 다음 포즈로 넘어갈지 여부 판단
- 실패 시 재촬영 처리
- 민증 촬영 및 확인 절차 진행

즉 등록 절차의 흐름 제어권이 이미 `FE`에 있다.

이 상태에서 `BE`가 별도의 오케스트레이션 API를 추가로 가지면 다음 문제가 생길 수 있다.

- 흐름 제어 책임이 `FE`와 `BE`에 중복된다
- API 구조가 불필요하게 복잡해진다
- 등록 절차 변경 시 `FE`, `BE`를 동시에 수정해야 할 가능성이 커진다

따라서 현재 단계에서는 `FE`가 플로우를 제어하고, `BE`는 각 단계의 검증/저장만 수행하는 편이 더 단순하고 실용적이다.

## 현재 대체 구조

### 1. 신분증 OCR 추출

- `POST /api/v1/identity/id-card/extract`

역할:

- 프론트가 촬영한 신분증 이미지를 `BE`로 전송
- `BE`가 `AI` OCR API를 호출
- 이름, 주민번호 일부, 문서 종류를 반환

### 2. 신분증 정보 최종 확인

- `POST /api/v1/identity/id-card/confirm`

역할:

- 사용자가 확인 또는 수정한 이름/주민번호 일부를 `BE`로 전송
- `BE`가 회원 정보와 비교
- 일치 여부와 다음 액션 반환

### 3. 얼굴 방향 검증

- `POST /api/v1/face/liveness/headpose/check`

역할:

- 프론트가 현재 포즈 촬영 이미지를 전송
- `BE`가 `AI` headpose API 호출
- 기대 방향과 실제 얼굴 방향이 일치하는지 검증

### 4. 얼굴 임베딩 저장

- `POST /api/v1/face/enroll`

역할:

- 프론트가 현재 포즈와 이미지를 전송
- `BE`가 `AI`에서 얼굴 임베딩 추출
- 임베딩을 암호화하여 저장
- 같은 `userId + pose` 조합은 갱신

## 등록 플로우 예시

현재 등록 플로우는 아래처럼 단계별 API 호출 조합으로 동작할 수 있다.

1. 프론트가 신분증 촬영
2. `POST /api/v1/identity/id-card/extract`
3. 사용자가 이름/주민번호 일부 확인 또는 수정
4. `POST /api/v1/identity/id-card/confirm`
5. 프론트가 `정면 1`
6. `POST /api/v1/face/liveness/headpose/check`
7. 통과 시 `POST /api/v1/face/enroll`
8. 프론트가 `정면 2`, `정면 3`, `좌`, `우` 순으로 반복
9. 프론트가 모든 필수 포즈가 끝났다고 판단하면 등록 완료 처리

즉 별도의 단일 오케스트레이션 API 없이도, 현재 기능 조합만으로 전체 등록 절차를 완성할 수 있다.

## 책임 분리

### FE 책임

- 사용자 안내 문구 출력
- 촬영 순서 제어
- 현재 단계 상태 관리
- 재촬영 처리
- 다음 API 호출 시점 결정

### BE 책임

- 인증/인가
- 입력 이미지 검증
- OCR 결과 반환
- 회원 정보 비교
- headpose 검증
- 얼굴 임베딩 저장

### AI 책임

- OCR 추론
- headpose 추론
- embedding 추출

## 장점

- 현재 프론트 구현 방식과 자연스럽게 맞는다
- `BE`가 플로우 상태까지 관리하지 않아도 된다
- API를 과도하게 합치지 않아 유지보수가 쉽다
- 단계별 실패 원인을 분리해서 처리하기 쉽다
- `OCR`, `headpose`, `embedding` 기능을 독립적으로 검증할 수 있다

## 한계

- 등록 완료 상태를 서버가 일괄 관리하지 않는다
- 등록 절차 순서를 `FE`가 책임져야 한다
- 프론트 구현 품질에 따라 사용자 경험이 달라질 수 있다

하지만 현재 프로젝트에서는 이 한계보다 구조 단순성과 개발 속도의 이점이 더 크다.

## 최종 판단

현재 프로젝트에서 `BE-032`는 별도 `오케스트레이션 API`를 만들기보다, 아래 방식으로 대체하는 것이 적절하다.

- `FE`가 등록 플로우를 제어한다
- `BE`는 단계별 검증/저장 API를 제공한다
- `AI`는 추론 전용으로 유지한다

따라서 현재 대체 구조는 다음 한 줄로 정리할 수 있다.

`통합 등록 API 대신, FE 주도 플로우와 BE 단계별 API 조합으로 페이스페이 등록을 처리한다.`
