# 발표 준비용 OCR · ArcFace 상세 정리

## 1. 문서 목적

이 문서는 발표 준비를 위해 `OCR`과 `ArcFace`를 프로젝트 관점에서 이해할 수 있게 정리한 자료다.

정리 범위는 다음과 같다.

- OCR이 무엇인지
- ArcFace가 무엇인지
- 우리 프로젝트에서 두 기술을 왜 같이 쓰는지
- 실제 코드 기준 동작 흐름
- 발표 때 강조하면 좋은 포인트
- 예상 질문과 답변

참고:

- 사용자 표현인 `acrface`는 일반적으로 `ArcFace`라고 부른다.
- 우리 프로젝트에서는 `OCR = 신분증 정보 추출`, `ArcFace = 얼굴 임베딩 추출 및 비교`라고 이해하면 된다.

---

## 2. 발표에서 먼저 말할 한 줄

### 2.1 10초 버전

`우리 서비스는 신분증의 문자 정보는 OCR로 확인하고, 얼굴은 ArcFace 임베딩으로 비교해서 FacePay 등록과 인증의 신뢰도를 높였습니다.`

### 2.2 30초 버전

`OCR은 주민등록증이나 운전면허증 이미지에서 이름과 주민번호 일부를 읽어오는 기술이고, ArcFace는 얼굴 이미지를 사람을 구분할 수 있는 숫자 벡터로 바꾸는 얼굴 인식 모델입니다. 우리 프로젝트는 OCR로 신분 확인을 하고, ArcFace로 얼굴 등록과 유사도 비교를 수행하며, 추가로 head pose 검증을 넣어서 사진 한 장만 들이대는 수준의 오용 가능성을 줄였습니다.`

### 2.3 1분 버전

`우리 프로젝트의 FacePay 등록은 크게 두 축으로 동작합니다. 첫 번째는 신분증 OCR입니다. 사용자가 주민등록증 또는 운전면허증을 비추면 AI 서버의 PaddleOCR가 문자를 읽고, 이름과 주민번호 앞 6자리, 뒤 첫 1자리를 추출합니다. 이후 사용자가 한 번 더 확인하고, 백엔드가 회원 정보와 비교해서 본인 여부를 확인합니다. 두 번째는 얼굴 인식입니다. 여기서는 ArcFace를 사용해서 얼굴 이미지를 512차원 임베딩으로 바꾸고, 저장된 임베딩과 코사인 유사도로 비교합니다. 그리고 단순 정면 사진만 저장하지 않고 좌우상하 head pose를 같이 확인해서 등록 과정의 신뢰도를 높였습니다. 즉 문자 기반 본인 확인과 얼굴 기반 생체 확인을 결합한 구조라고 설명할 수 있습니다.`

## 3. 핵심 용어 설명

### 3.1 OCR이란

OCR은 `Optical Character Recognition`의 줄임말이다.

쉽게 말하면:

- 이미지 안에 있는 글자를 읽어서 텍스트로 바꾸는 기술

우리 프로젝트에서는:

- 주민등록증
- 운전면허증

이 두 문서에서 아래 정보를 꺼내는 데 사용한다.

- 이름
- 주민등록번호 앞 6자리
- 주민등록번호 뒤 첫 1자리
- 문서 종류

즉, OCR은 `이 신분증에서 어떤 문자가 보이는지`를 읽는 역할이다.

### 3.2 ArcFace란

ArcFace는 얼굴 인식 분야에서 많이 쓰이는 `face recognition model`이다.

쉽게 말하면:

- 얼굴 사진을 바로 사람 이름으로 분류하는 모델이 아니라
- 얼굴을 비교 가능한 숫자 벡터로 바꿔주는 모델

우리 프로젝트에서는:

- 얼굴 이미지를 `512차원 embedding`으로 변환
- 저장된 embedding과 새로 들어온 embedding을 비교
- 코사인 유사도로 동일인 여부를 판단

즉, ArcFace는 `이 얼굴이 누구와 얼마나 비슷한가`를 계산하기 위한 얼굴 특징 추출기다.

## 4. 왜 OCR과 ArcFace를 같이 쓰는가

둘의 역할은 겹치지 않는다.

OCR이 답하는 질문:

- `신분증에 적힌 사람이 누구인가`

ArcFace가 답하는 질문:

- `지금 카메라 앞 사람의 얼굴이 등록된 얼굴과 같은가`

따라서 둘을 같이 쓰는 이유는 다음과 같다.

1. OCR만 있으면 종이 신분증 정보만 읽을 수 있고 실제 얼굴 일치 여부는 알 수 없다.
2. ArcFace만 있으면 얼굴 비교는 가능하지만, 초기 등록 시 그 얼굴이 실제 회원 정보와 연결된 사람인지 보강이 약하다.
3. OCR과 얼굴 인식을 합치면 `신원 정보 + 얼굴 특징`을 모두 확인하는 구조가 된다.

발표에서는 이렇게 말하면 된다.

`OCR은 문서 기반 본인 확인이고, ArcFace는 얼굴 기반 본인 확인입니다. 둘을 결합해서 등록 신뢰도를 높였습니다.`

## 5. 우리 프로젝트 전체 구조

### 5.1 한 줄 구조

`Android FE -> Spring BE -> FastAPI AI -> PaddleOCR / ArcFace`

### 5.2 구성 요소별 역할

| 구성 | 역할 |
|---|---|
| Android FE | 카메라 미리보기, 사용자 가이드, 이미지 업로드, 결과 표시 |
| Spring BE | 인증/인가, 공개 API 제공, AI 서버 중계, 최종 비교/판정 |
| FastAPI AI | OCR 추론, 얼굴 임베딩 추출, head pose 검증 |
| PaddleOCR | 신분증 문자 추출 |
| ArcFace | 얼굴 임베딩 추출 |

### 5.3 왜 AI 서버를 분리했는가

이유는 분명하다.

- OCR과 얼굴 인식은 Python 생태계 라이브러리 의존성이 크다.
- Spring 서버에 직접 얹으면 배포와 운영 복잡도가 올라간다.
- AI 모델 교체 시 Java 서버를 크게 수정하지 않아도 된다.

즉 발표에서는:

`백엔드는 비즈니스 로직과 인증을 담당하고, AI 서버는 추론 전용으로 분리했습니다.`

라고 설명하면 된다.

## 6. OCR을 우리 프로젝트에서 어떻게 쓰는가

### 6.1 사용자 흐름

1. 사용자가 얼굴 등록을 마친다.
2. 신분증 OCR 단계로 이동한다.
3. 사용자가 주민등록증 또는 운전면허증을 카메라에 비춘다.
4. 프론트가 일정 시간 안정적으로 인식되면 OCR 추출 API를 호출한다.
5. AI 서버가 OCR 결과를 반환한다.
6. 프론트가 추출된 이름과 주민번호 일부를 확인 화면에 보여준다.
7. 사용자가 확인 또는 수정한다.
8. 백엔드가 로그인 사용자 정보와 비교한다.

핵심은 `추출`과 `확인`이 분리되어 있다는 점이다.

### 6.2 실제 API 흐름

프론트 공개 API:

- `POST /api/v1/identity/id-card/extract`
- `POST /api/v1/identity/id-card/confirm`

백엔드가 호출하는 AI 내부 API:

- `POST /internal/v1/ocr/id-card/extract`

### 6.3 코드 기준 책임 분리

프론트:

- `naedafront/app/src/main/java/com/example/naedafront/data/remote/FaceRegistrationRemote.kt`
- `naedafront/app/src/main/java/com/example/naedafront/ui/screen/facepay/FaceRegisterFlowScreen.kt`

백엔드:

- `naeda/src/main/java/com/ssafy/naeda/domain/identity/controller/ResidentIdVerifyController.java`
- `naeda/src/main/java/com/ssafy/naeda/domain/identity/service/ResidentIdVerifyService.java`
- `naeda/src/main/java/com/ssafy/naeda/domain/identity/client/ResidentIdOcrClient.java`

AI:

- `AI/app/api/internal_resident_id_ocr.py`
- `AI/app/core/resident_ocr.py`

### 6.4 OCR 내부 동작

AI 서버는 아래 순서로 동작한다.

1. 이미지 바이트를 읽는다.
2. 업로드 크기 제한을 검사한다.
3. `resident_ocr_provider` 설정을 확인한다.
4. `paddleocr` provider면 전처리 후 OCR을 수행한다.
5. OCR 텍스트를 후처리해 문서 종류, 이름, 주민번호 일부를 추출한다.
6. 결과를 백엔드로 반환한다.

### 6.5 OCR 전처리

현재 코드 기준 전처리는 비교적 단순하다.

- 이미지 디코딩
- grayscale 변환
- intensity normalization
- 다시 BGR 변환 후 OCR 입력

이 전처리의 목적은:

- 글자 대비를 조금 더 안정화
- 카드 촬영 환경이 달라도 OCR 입력을 일정하게 맞추기 위함

### 6.6 문서 종류 판별

코드상 지원 문서는 두 가지다.

- `RESIDENT_ID`
- `DRIVER_LICENSE`

판별 방식은 현재 키워드 기반이다.

- `주민등록증`이 보이면 주민등록증
- `운전면허`, `운전면허증`이 보이면 운전면허증

즉 문서 분류를 별도 딥러닝 모델로 하는 것이 아니라, OCR 텍스트에서 키워드를 찾는 방식이다.

### 6.7 이름 추출 방식

이름은 생각보다 까다롭다.

이유:

- 주민등록증과 운전면허증의 배치가 다르다.
- `성명`과 실제 이름이 한 줄에 붙어 있지 않은 경우가 있다.
- 지역명, 기관명, 발급기관 텍스트가 이름으로 잘못 잡힐 수 있다.

현재 후처리 전략은 대략 이렇다.

1. `성명`, `이름` 라벨 근처 텍스트를 우선 탐색
2. 같은 줄 또는 가까운 줄의 한글 토큰을 합쳐 이름 후보 생성
3. 주민번호 근처 텍스트도 후보로 탐색
4. `특별시`, `경찰청`, `시장` 같은 기관성 텍스트는 blacklist로 제외

즉 OCR 정확도는 모델 하나만의 문제가 아니라, 후처리 규칙 설계의 영향도 크다.

### 6.8 주민번호 추출 방식

주민번호는 정규식 기반으로 처리한다.

현재 사용하는 값은:

- 앞 6자리
- 뒤 첫 1자리

즉 전체 주민번호를 저장하거나 비교하는 것이 아니라, 최소한의 비교 정보만 사용한다.

### 6.9 왜 OCR 결과를 바로 확정하지 않고 사용자 확인을 거치는가

이건 발표에서 좋은 포인트다.

이유:

- OCR은 항상 오인식 가능성이 있다.
- 주민등록증의 이름처럼 레이아웃에 따라 흔들리는 부분이 있다.
- 사용자가 한 번 확인하면 잘못된 자동 판정 리스크를 줄일 수 있다.

즉:

`우리 프로젝트는 OCR 결과를 그대로 확정하지 않고, 사용자 확인 단계를 둬서 안정성을 높였습니다.`

### 6.10 OCR 확인 단계에서 실제 비교하는 값

백엔드는 최종 확인 시 아래를 비교한다.

- 회원 이름
- 회원 주민번호 7자리 정보

비교 기준은:

- 이름은 공백 제거 후 비교
- 주민번호는 숫자만 남긴 뒤 비교

즉 OCR 결과 원문 전체를 신뢰하는 것이 아니라, 사용자 확인 후 보정된 값으로 비교한다.

## 7. ArcFace를 우리 프로젝트에서 어떻게 쓰는가

### 7.1 사용자 흐름

1. 사용자가 여러 방향의 얼굴을 촬영한다.
2. 프론트가 각 방향을 가이드한다.
3. 백엔드가 얼굴 등록 API를 호출한다.
4. AI 서버가 ArcFace로 얼굴 임베딩을 추출한다.
5. 백엔드는 해당 embedding을 사용자별 포즈별로 저장한다.
6. 이후 결제 또는 얼굴 검색 시 다시 embedding을 추출하고 비교한다.

### 7.2 실제 API 흐름

공개 API:

- `POST /api/v1/face/enroll`
- `POST /api/v1/face/search`
- `POST /api/v1/face/liveness/headpose/check`

AI 내부 API:

- `POST /internal/v1/embeddings/extract`
- `POST /internal/v1/liveness/headpose/check`

### 7.3 ArcFace가 하는 일

ArcFace는 얼굴 이미지를 바로 `홍길동`이라고 분류하지 않는다.

대신 다음을 수행한다.

- 얼굴 검출
- 얼굴 특징 추출
- 512차원 숫자 벡터 생성

이 벡터를 `embedding`이라고 한다.

이 embedding의 의미는:

- 같은 사람일수록 벡터 방향이 비슷하고
- 다른 사람일수록 벡터 방향이 멀어진다

그래서 비교 시 `코사인 유사도`를 사용한다.

### 7.4 왜 512차원인가

코드 기준 ArcFace 응답은 `dim = 512`다.

발표에서는 이렇게 설명하면 충분하다.

`512차원은 얼굴 특징을 충분히 표현하면서도 비교 연산이 가능한 실무형 벡터 길이입니다. 우리 프로젝트는 이 512차원 벡터를 DB에 저장하고, 나중에 코사인 유사도로 비교합니다.`

### 7.5 현재 ArcFace 처리 방식

AI 서버의 `arcface.py`는 아래와 같이 동작한다.

1. `InsightFace FaceAnalysis`로 얼굴 탐지
2. 얼굴이 0개면 `NO_FACE`
3. 2개 이상이면 `MULTIPLE_FACES`
4. 얼굴 1개면 embedding 추출
5. L2 normalize 수행
6. 512차원인지 검증
7. 품질 점수와 yaw/pitch/roll을 함께 반환

즉 단순히 벡터만 주는 것이 아니라:

- `quality_score`
- `yaw`
- `pitch`
- `roll`

도 함께 반환해서 후속 판단에 활용할 수 있다.

### 7.6 왜 normalize를 하는가

정규화의 목적은 비교 안정성이다.

정규화 후에는:

- 벡터 크기보다 방향 비교가 중요해진다
- 코사인 유사도 계산이 안정적이다

발표에서는:

`ArcFace가 뽑은 임베딩은 정규화 후 저장해서, 이후 코사인 유사도로 사람 간 유사도를 계산합니다.`

라고 말하면 된다.

### 7.7 백엔드 저장 방식

현재 DB 저장 기준으로는 원본 얼굴 이미지가 아니라 `embedding`이 저장된다.

저장 테이블:

- `face_embeddings`

저장 필드 핵심:

- `user_id`
- `pose`
- `embedding`

즉 발표에서 보안 포인트로:

`최소한 DB 저장 기준으로는 원본 얼굴 사진 대신 얼굴 특징 벡터를 저장합니다.`

라고 설명할 수 있다.

단, 업로드 과정에서 이미지는 FE -> BE -> AI로 전달되므로 `전송 자체가 사라지는 것은 아니고, 영구 저장 기준이 embedding 중심`이라는 점은 정확히 구분해서 말하는 것이 좋다.

### 7.8 유사도 비교와 임계값

현재 백엔드 `FaceService` 기준:

- `matchThreshold = 0.7`
- `ambiguousThreshold = 0.65`

판정은 아래와 같다.

- `0.7 이상`이면 일치
- `0.65 이상 ~ 0.7 미만`이면 애매
- 그보다 낮으면 불일치

이 값은 모델 자체가 아니라 서비스 정책 값이다.

즉 발표에서는:

`모델 출력만으로 바로 결정하지 않고, 서비스에서 임계값을 두고 match / ambiguous / no match로 구분합니다.`

라고 설명하면 좋다.

---

## 8. head pose 검증은 왜 필요한가

우리 프로젝트는 ArcFace만 쓰는 것이 아니라 `head pose` 검증도 함께 쓴다.

이유:

- 정면 사진 한 장만 등록하면 다양성이 부족하다.
- 좌우상하 포즈를 유도하면 사용자가 실제로 카메라 앞에서 움직이고 있는지 일정 부분 확인할 수 있다.
- 여러 각도의 embedding을 저장하면 나중에 실사용 환경 변화에 더 견고해질 수 있다.

현재 코드 기준 head pose는:

- `front`
- `left`
- `right`
- `up`
- `down`

을 지원한다.

AI는 landmark와 pose를 사용해서 `yaw`, `pitch` 기반으로 방향을 계산한다.

중요한 점:

- 이것은 완전한 anti-spoofing 모델이라기보다
- `가벼운 liveness/자세 검증 레이어`에 가깝다

즉 발표에서 과장하면 안 된다.

좋은 표현:

`저희는 별도 고가의 안티스푸핑 모델 대신, head pose 검증을 추가해서 등록 과정의 신뢰도를 높였습니다. 완전한 딥페이크 방어를 주장하는 구조는 아닙니다.`

---

## 9. 우리 프로젝트 기준 장점

### 9.1 OCR 측면 장점

- 외부 OCR API 의존 없이 내부 AI 서버에서 처리 가능
- 주민등록증과 운전면허증 둘 다 지원
- 추출 결과를 바로 확정하지 않고 사용자 확인 단계 제공
- provider 구조가 있어 `mock`, `paddleocr`, 다른 OCR 엔진으로 교체 가능

### 9.2 ArcFace 측면 장점

- 얼굴을 직접 분류하는 대신 임베딩 비교 기반이라 유연함
- 포즈별 등록이 가능해 실제 사용 환경에 대응하기 좋음
- 백엔드가 임계값 정책을 별도로 가질 수 있음
- 원본 이미지 대신 embedding 중심 저장 구조

### 9.3 시스템 구조 측면 장점

- FE, BE, AI 역할이 분리돼 유지보수가 좋음
- AI 모델을 바꿔도 공개 API 계약은 비교적 유지 가능
- 장애 시 어느 레이어 문제인지 분리해서 추적하기 쉬움

---

## 10. 우리 프로젝트 기준 한계와 리스크

### 10.1 OCR 한계

- 촬영 품질이 나쁘면 OCR이 흔들린다.
- 주민등록증 이름은 문서 레이아웃 특성상 운전면허증보다 까다롭다.
- 키워드 기반 문서 분류라 극단적인 가림이나 잘림에 취약할 수 있다.

### 10.2 ArcFace 한계

- lighting, angle, blur, occlusion 영향을 받는다.
- 임계값 설정이 너무 낮으면 오인식, 너무 높으면 거부율 증가
- face embedding 비교만으로는 완전한 생존성 검증이 아니다.

### 10.3 운영 한계

- OCR과 얼굴 인식은 CPU 환경에서 지연이 커질 수 있다.
- PaddleOCR 모델 초기화와 캐시 관리가 필요하다.
- AI 서버가 불안정하면 FE/BE는 정상이어도 등록 경험이 깨진다.

발표에서 중요한 태도:

- `완벽하다`고 말하지 말고
- `정확도와 UX를 계속 튜닝 중인 구조`라고 설명하는 편이 좋다

## 11. 발표용 추천 설명 흐름

발표에서 이 순서로 설명하면 자연스럽다.

### 11.1 1단계: 문제 정의

`FacePay를 등록하려면 사용자가 본인이라는 것을 어느 정도 신뢰성 있게 확인해야 했습니다. 그래서 저희는 문서 정보 확인과 얼굴 생체 정보를 같이 사용했습니다.`

### 11.2 2단계: OCR 설명

`먼저 신분증 OCR로 이름과 주민번호 일부를 읽습니다. 다만 OCR은 오인식 가능성이 있어서 바로 확정하지 않고, 확인 화면에서 사용자가 한 번 더 검증하도록 했습니다.`

### 11.3 3단계: ArcFace 설명

`얼굴 쪽은 ArcFace를 이용했습니다. ArcFace는 얼굴을 512차원 임베딩으로 바꾸고, 저희는 이를 저장해서 이후 코사인 유사도로 비교합니다.`

### 11.4 4단계: 보강 설명

`그리고 정면만 보는 것이 아니라 좌우상하 포즈를 확인해서 등록 과정의 신뢰도를 조금 더 높였습니다.`

### 11.5 5단계: 아키텍처 설명

`앱은 카메라와 UX를 담당하고, 백엔드는 인증과 최종 판정을 담당하며, AI 서버는 OCR과 얼굴 추론만 담당하도록 역할을 분리했습니다.`

### 11.6 6단계: 한계 인정

`현재 구조는 실사용 가능한 수준으로 구현했지만, OCR 정확도와 anti-spoofing 강도는 더 고도화할 수 있는 영역입니다.`

## 12. 예상 질문과 답변

아래는 발표에서 나올 가능성이 높은 질문들이다.

### Q1. OCR이 정확히 뭐예요

`이미지 안에 있는 글자를 읽어서 텍스트로 바꾸는 기술입니다. 저희 프로젝트에서는 신분증에서 이름과 주민번호 일부를 추출하는 데 사용했습니다.`

### Q2. ArcFace는 정확히 뭐예요

`얼굴을 사람 구분이 가능한 숫자 벡터, 즉 embedding으로 바꾸는 얼굴 인식 모델입니다. 저희는 이 embedding을 저장하고 새 이미지와 비교합니다.`

### Q3. 왜 OCR과 ArcFace를 둘 다 썼나요

`OCR은 문서 정보 확인, ArcFace는 얼굴 동일인 비교라는 역할이 다릅니다. 하나만 쓰면 한쪽 검증이 비어 있어서 둘을 결합했습니다.`

### Q4. 왜 백엔드에서 직접 OCR 안 하고 AI 서버를 따로 뒀나요

`PaddleOCR나 InsightFace는 Python 의존성이 크고 모델 운영 성격이 강합니다. 백엔드는 인증과 비즈니스 로직에 집중하고, AI 추론은 별도 서버로 분리하는 편이 유지보수와 확장에 유리합니다.`

### Q5. 왜 외부 OCR API를 안 쓰고 PaddleOCR를 썼나요

`비용과 의존성을 줄이고, 내부 구조를 직접 제어하기 위해서입니다. 또 provider 구조를 만들어서 나중에 다른 OCR 엔진으로 바꾸기 쉽도록 설계했습니다.`

### Q6. OCR 결과를 바로 믿지 않고 사용자가 다시 확인하게 한 이유는 뭔가요

`신분증 촬영 환경에서는 반사광, 기울기, 흔들림 때문에 오인식이 발생할 수 있습니다. 자동 추출 후 사용자 확인 단계를 넣어서 안정성을 높였습니다.`

### Q7. 주민등록증 이름 인식이 어려운 이유는 뭔가요

`주민등록증은 이름 라벨과 실제 이름이 떨어져 있거나 기관명, 지역명 같은 한글 텍스트가 많아서 이름 후보가 섞이기 쉽습니다. 그래서 OCR 모델 자체뿐 아니라 후처리 규칙이 중요합니다.`

### Q8. 얼굴 이미지를 DB에 저장하나요

`현재 확인한 저장 구조 기준으로는 얼굴 원본 대신 embedding을 DB에 저장합니다. 다만 업로드 과정에서는 이미지가 FE, BE, AI를 거쳐 추론에 사용됩니다.`

### Q9. embedding만 저장하면 원본 얼굴을 복원할 수 있나요

`embedding은 얼굴 비교를 위한 특징 벡터라서 일반적인 원본 이미지 저장과는 다릅니다. 다만 생체정보 성격은 있으므로 보호 대상으로 보는 것이 맞습니다.`

### Q10. 왜 512차원인가요

`현재 ArcFace 모델이 반환하는 표준 embedding 길이입니다. 얼굴 특징을 충분히 담으면서 비교 연산도 가능한 수준이라 실무에서 많이 사용됩니다.`

### Q11. 유사도 기준은 어떻게 정했나요

`현재 서비스에서는 0.7을 match, 0.65를 ambiguous 기준으로 두고 있습니다. 이 값은 모델 고정값이 아니라 서비스 정책이며, 데이터와 오탐/미탐을 보면서 조정할 수 있습니다.`

### Q12. head pose 검증은 왜 필요한가요

`등록 시 사용자가 실제로 카메라 앞에서 움직이고 있는지 확인하는 보조 수단이고, 여러 각도의 얼굴 특징을 저장하기 위한 목적도 있습니다.`

### Q13. 그러면 이게 완전한 liveness인가요

`엄밀히 말하면 고급 anti-spoofing 모델 수준의 완전한 liveness는 아닙니다. 현재는 head pose 기반의 경량 검증 레이어라고 설명하는 것이 정확합니다.`

### Q14. OCR과 얼굴 인식 중 어느 쪽이 더 불안정한가요

`현재 경험상 OCR은 촬영 품질과 문서 레이아웃에 크게 좌우되고, 얼굴 인식은 조명과 각도 영향이 큽니다. 특히 주민등록증 이름 OCR은 후처리 튜닝의 영향이 컸습니다.`

### Q15. 주민등록증과 운전면허증을 어떻게 구분하나요

`OCR로 읽힌 텍스트에서 주민등록증, 운전면허 같은 키워드를 찾는 방식으로 구분합니다.`

### Q16. 왜 주민번호 전체를 다 쓰지 않고 일부만 쓰나요

`민감정보 최소화 관점에서 필요한 최소 비교 정보만 사용하려는 방향입니다. 현재 비교도 이름과 주민번호 7자리 기준으로 수행합니다.`

### Q17. AI 서버가 죽으면 어떻게 되나요

`백엔드는 OCR_UNAVAILABLE, AI_TIMEOUT 같은 오류를 서비스 오류로 변환해 전달합니다. 기능은 영향을 받지만, 레이어가 분리돼 있어 원인 추적과 재기동은 수월합니다.`

### Q18. CPU로도 운영 가능한가요

`가능은 하지만 성능과 지연은 GPU보다 불리할 수 있습니다. 현재 설정도 CPUExecutionProvider 기준이어서 동작은 가능하지만, 트래픽이 커지면 튜닝이 필요할 수 있습니다.`

### Q19. mock provider는 뭐였나요

`개발 중 흐름 확인용 가짜 OCR 응답입니다. 실제 OCR 검증은 paddleocr provider로 해야 하고, mock은 개발 편의를 위한 임시 모드라고 보면 됩니다.`

### Q20. 왜 사용자가 직접 이름이나 주민번호 일부를 수정할 수 있게 했나요

`OCR은 보조 수단이고, 최종 확인 정확도를 높이기 위해 사용자 보정 가능성을 열어둔 것입니다. 특히 이름은 레이아웃 영향을 많이 받기 때문에 이 단계가 중요합니다.`

### Q21. 이 프로젝트에서 개인정보 보호는 어떻게 설명하면 되나요

`얼굴은 원본 사진을 장기 저장하는 대신 embedding 중심으로 저장하고, OCR도 필요한 최소 정보만 비교하는 방향입니다. 다만 생체정보와 신분정보를 다루므로 전송 구간 보호와 저장 정책은 계속 강화해야 합니다.`

### Q22. 향후 개선 방향은 무엇인가요

`OCR 정확도 개선, 더 강한 anti-spoofing 도입, threshold 튜닝 자동화, 실제 운영 데이터 기반 평가 체계 구축이 대표적인 다음 단계입니다.`

## 13. 발표에서 강조하면 좋은 포인트

### 13.1 기술 이름보다 역할을 먼저 설명하기

좋은 설명:

`OCR은 문서를 읽는 기술이고, ArcFace는 얼굴을 비교 가능한 숫자로 바꾸는 기술입니다.`

나쁜 설명:

`PaddleOCR와 ArcFace를 썼습니다.`

이유는 기술 이름만 말하면 듣는 사람이 바로 이해하지 못하기 때문이다.

### 13.2 정확도보다 구조적 이유를 강조하기

좋은 포인트:

- 왜 FE, BE, AI를 분리했는가
- 왜 OCR 후 확인 단계를 넣었는가
- 왜 얼굴은 embedding으로 저장하는가
- 왜 head pose를 추가했는가

### 13.3 한계를 숨기지 않기

발표에서는 한계를 인정하는 답변이 오히려 신뢰를 준다.

예:

`현재 구조는 실사용 가능한 수준으로 구현했지만, OCR 정확도와 anti-spoofing은 계속 고도화가 필요한 영역입니다.`
