## 1. ArcFace 관련 질문

### Q1. 왜 얼굴 인식 모델로 ArcFace를 선택했나요?

ArcFace는 얼굴을 바로 분류하는 방식이 아니라 `비교 가능한 임베딩`을 뽑아주는 모델이라 서비스에 붙이기 좋다. 우리 프로젝트는 등록된 얼굴과 새 얼굴을 직접 비교해야 하므로, 임베딩 기반 모델이 자연스럽다. 또 현재 구현은 `InsightFace FaceAnalysis`를 써서 비교적 안정적으로 붙일 수 있었다.

### Q2. FaceNet이나 다른 얼굴 인식 모델 대신 ArcFace를 쓴 이유는 뭔가요?

핵심은 `임베딩 품질`, `오픈소스 생태계`, `실서비스 적용 편의성`이다. ArcFace 계열은 얼굴 인식에서 널리 검증된 편이고, InsightFace를 통해 탐지와 임베딩 추출을 한 번에 가져가기 좋았다. 프로젝트 일정과 구현 리스크를 고려하면 ArcFace가 가장 실용적이었다.

### Q3. ArcFace는 정확히 어떤 출력을 주나요?

현재 프로젝트에서는 `512차원 embedding`을 반환한다. 추가로 얼굴 검출 점수 기반 `quality_score`, 그리고 `yaw`, `pitch`, `roll`도 함께 얻는다.

### Q4. 왜 512차원 임베딩을 쓰나요?

현재 사용 중인 ArcFace 계열 모델이 기본적으로 512차원 얼굴 특징 벡터를 반환하기 때문이다. 이 정도 차원은 얼굴 구분력을 충분히 확보하면서 비교 연산도 감당 가능한 수준이다.

### Q5. ArcFace가 사람을 직접 분류하는 건가요?

아니다. ArcFace는 `이 사람이 홍길동이다`라고 직접 분류하지 않는다. 얼굴을 비교 가능한 벡터로 변환하고, 서비스가 저장된 벡터와 비교해서 같은 사람인지 판단한다.

### Q6. ArcFace 결과를 DB에 어떻게 저장하나요?

원본 얼굴 사진이 아니라 `embedding`을 저장한다. 현재 저장 구조는 `user_id`, `pose`, `embedding` 기준이다.

### Q7. embedding을 저장하면 어떤 장점이 있나요?

- 원본 이미지를 매번 직접 비교하지 않아도 된다.
- 빠르게 유사도 계산이 가능하다.
- 서비스 정책에 맞게 임계값 조정이 가능하다.
- 저장 단위를 얼굴 특징 벡터로 줄일 수 있다.

### Q8. ArcFace 임베딩은 왜 정규화하나요?

코사인 유사도 비교를 안정적으로 하기 위해서다. 벡터 크기보다 방향 비교가 중요해지고, 같은 사람/다른 사람 간 비교가 더 일관되게 된다.

### Q9. 현재 ArcFace 모델 설정은 어떻게 되나요?

코드 기준 기본값은 다음과 같다.

- 모델명: `buffalo_l`
- provider: `CPUExecutionProvider`
- det_size: `320`

즉 현재는 CPU 환경을 기본으로 두고 있다.

### Q10. det_size 320은 무슨 의미인가요?

얼굴 검출 단계에서 사용하는 입력 크기 관련 설정이다. 너무 작으면 작은 얼굴 검출이 약해질 수 있고, 너무 크면 속도가 느려질 수 있다. 현재는 속도와 안정성의 균형점으로 320을 사용 중이다.

### Q11. 왜 CPUExecutionProvider를 쓰나요?

현재 프로젝트는 GPU 의존 없이 동작 가능한 구성을 우선했다. 배포와 실행 환경 제약을 고려하면 CPU 기준으로 먼저 안정화하는 것이 현실적이었다.

### Q12. 그러면 GPU를 쓰면 더 좋아지나요?

대체로 추론 속도는 좋아질 가능성이 크다. 다만 현재 규모에서는 CPU로도 동작 가능했고, 운영 복잡도까지 고려해 기본값은 CPU로 뒀다.

### Q13. 얼굴이 여러 개 잡히면 어떻게 처리하나요?

AI 서버에서 바로 실패 처리한다. 현재 로직은 얼굴이 0개면 `NO_FACE`, 2개 이상이면 `MULTIPLE_FACES`를 반환한다.

### Q14. 얼굴이 검출됐는데 embedding이 이상하면 어떻게 되나요?

embedding이 없거나, norm이 0이거나, 차원이 512가 아니면 `AI_UNAVAILABLE`로 본다. 즉 서비스에서 신뢰할 수 없는 결과는 실패로 처리한다.

### Q15. 얼굴 유사도는 어떤 방식으로 계산하나요?

백엔드에서 `코사인 유사도`를 계산한다. 같은 사람일수록 1에 가까워지고, 다를수록 낮아진다.

### Q16. 현재 match 기준은 어떻게 잡혀 있나요?

백엔드 기준으로:

- `0.7 이상`: match
- `0.65 이상 ~ 0.7 미만`: ambiguous
- 그 미만: no match

이 값은 모델 고정값이 아니라 서비스 정책값이다.

### Q17. 왜 ambiguous 구간을 두나요?

얼굴 인식은 확률적 요소가 있어서, 특정 구간은 바로 승인이나 거절로 보내기보다 추가 인증으로 넘기는 것이 안전하다. 그래서 `애매한 구간`을 둔다.

### Q18. ArcFace만으로 본인 인증을 끝내도 되지 않나요?

현재 프로젝트는 그렇게 보지 않았다. 초기 등록에서는 신분증 OCR도 함께 사용했고, 인증 흐름에서도 상황에 따라 추가 인증을 요구할 수 있게 설계했다.

### Q19. ArcFace가 조명이나 각도 영향을 받지 않나요?

받는다. 얼굴 인식 모델은 일반적으로 조명, blur, 각도, 표정, 가림의 영향을 받는다. 그래서 여러 포즈 등록과 head pose 확인을 함께 넣었다.

### Q20. ArcFace 임베딩만으로 원본 얼굴을 복원할 수 있나요?

일반적인 원본 이미지 저장과는 다르지만, 생체 특징을 담고 있는 민감 정보라는 점은 변하지 않는다. 그래서 보안적으로는 여전히 보호 대상이다.

## 2. OCR 관련 질문

### Q21. OCR 모델로 왜 PaddleOCR를 썼나요?

한국어 지원, 오픈소스, 자체 호스팅 가능성, Python 기반 연동 편의성 때문이다. 외부 유료 API에 묶이지 않고 내부 서비스로 운영하기 적합했다.

### Q22. PaddleOCR는 프로젝트에서 정확히 어디서 쓰이나요?

AI 서버의 신분증 OCR 단계에서 사용된다. 프론트가 올린 이미지를 백엔드가 AI 서버로 전달하면, AI 서버가 PaddleOCR로 텍스트를 읽는다.

### Q23. OCR에서 별도 문서 분류 모델을 쓰나요?

현재는 아니다. 문서 분류를 별도 딥러닝 모델로 하지 않고, OCR 결과 텍스트에서 `주민등록증`, `운전면허` 같은 키워드를 찾아 문서 종류를 판별한다.

### Q24. OCR 처리 순서는 어떻게 되나요?

현재 기준 순서는 다음과 같다.

1. 이미지 디코딩
2. grayscale 변환
3. normalization
4. PaddleOCR 실행
5. OCR 결과 flatten
6. 문서 종류 판별
7. 주민번호 일부 추출
8. 이름 추출
9. confidence 계산

### Q25. OCR 전처리를 왜 하나요?

신분증 촬영 환경은 조명, 그림자, 흔들림이 일정하지 않다. grayscale과 normalization으로 입력 분포를 조금 더 안정화하려는 목적이다.

### Q26. OCR은 주민등록증과 운전면허증 둘 다 처리하나요?

그렇다. 현재 지원 문서는 `RESIDENT_ID`와 `DRIVER_LICENSE` 두 가지다.

### Q27. OCR이 추출하는 값은 정확히 뭐죠?

현재 추출값은 다음과 같다.

- `documentType`
- `documentMatched`
- `name`
- `residentFront6`
- `residentBackFirst1`
- `provider`
- `confidence`

### Q28. 왜 주민번호 전체가 아니라 일부만 추출하나요?

민감정보 최소화 관점 때문이다. 서비스 확인에 필요한 최소 범위만 사용하려는 방향이다.

### Q29. 주민번호는 어떻게 찾나요?

정규식으로 찾는다. `6자리 + 뒤 첫 1자리` 패턴을 OCR 텍스트에서 추출하는 방식이다.

### Q30. 이름 추출은 왜 어려운가요?

이름은 레이아웃 영향을 많이 받는다. `성명` 라벨과 이름이 붙어 있지 않거나, 기관명/지역명이 같이 존재해서 이름 후보를 헷갈리기 쉽다.

### Q31. 이름은 어떤 방식으로 추출하나요?

현재는 규칙 기반 후처리다.

- `성명`, `이름` 라벨 탐색
- 같은 줄 또는 가까운 줄의 한글 토큰 결합
- 주민번호 주변 텍스트도 후보 탐색
- 지역명, 기관명 등 blacklist 제거

### Q32. 왜 OCR 결과를 바로 믿지 않고 확인 화면을 두나요?

OCR은 잘못 읽을 수 있기 때문이다. 특히 이름처럼 레이아웃 민감도가 높은 항목은 사용자 확인을 한 번 거치는 것이 훨씬 안전하다.

### Q33. OCR confidence는 어떻게 계산하나요?

현재는 OCR entry들의 confidence 평균을 기반으로 하되, 최소값 설정을 반영해서 계산한다. 즉 완전한 calibrated probability라기보다 서비스 참고용 점수다.

### Q34. OCR provider 구조를 둔 이유는 뭔가요?

지금은 `mock`, `paddleocr`, `disabled` 구조다. 이 구조를 두면 개발 중 mock 사용, 실제 운영 시 paddleocr 사용, 나중에 다른 엔진으로 교체하는 것도 쉬워진다.

### Q35. mock provider는 왜 필요했나요?

개발 초기에 전체 회원가입 플로우를 막지 않고 UI와 API 연결을 먼저 확인하기 위해서다. 다만 실검증 단계에서는 반드시 실제 OCR provider로 바꿔야 한다.

### Q36. OCR이 실패하면 어떤 오류가 나나요?

대표적으로:

- `OCR_EXTRACTION_FAILED`
- `OCR_UNAVAILABLE`
- `INVALID_IMAGE`

백엔드는 이를 사용자용 오류로 다시 매핑한다.

### Q37. OCR 정확도를 높이기 위해 앞으로 뭘 할 수 있나요?

- 실제 신분증 샘플 기반 후처리 튜닝
- 문서 종류별 전용 룰 분리
- 카드 영역 검출 추가
- 더 강한 전처리
- OCR 엔진 교체 또는 ensemble

### Q38. 외부 OCR API를 쓰면 더 정확하지 않나요?

그럴 수는 있다. 하지만 비용, 개인정보 외부 전송, vendor lock-in, 운영 제어권 문제가 생긴다. 현재 프로젝트는 내부 운영 통제와 구조 단순성을 더 중시했다.

### Q39. 왜 OCR도 백엔드에서 직접 안 하고 AI 서버에 둔 건가요?

PaddleOCR는 Python 중심 라이브러리이고, 모델과 추론 의존성이 있다. Java Spring에 직접 넣기보다 AI 서버에 분리하는 편이 자연스럽다.

### Q40. OCR 결과를 최종적으로 누가 검증하나요?

최종 비교는 백엔드가 한다. OCR이 읽은 값을 사용자가 확인하고, 백엔드가 로그인 사용자 정보와 비교해서 검증 결과를 확정한다.

## 3. head pose / liveness 관련 질문

### Q41. head pose 검증은 왜 넣었나요?

사용자가 실제로 카메라 앞에서 움직이고 있는지 확인하는 보조 수단이고, 여러 방향 얼굴 데이터를 확보하기 위한 목적도 있다.

### Q42. head pose는 어떻게 판정하나요?

AI 서버에서 얼굴 landmark와 pose를 바탕으로 `yaw`, `pitch`를 계산해 `front`, `left`, `right`, `up`, `down` 중 하나로 분류한다.

### Q43. 이것이 완전한 anti-spoofing인가요?

아니다. 현재는 경량 head pose 검증 레이어에 가깝다. 정교한 위조 탐지나 딥페이크 방어까지 보장한다고 말하면 과장이다.

### Q44. 그래도 head pose를 쓰는 이유는 뭔가요?

구현 복잡도 대비 효율이 좋기 때문이다. 별도 고가 안티스푸핑 모델 없이도 등록 과정의 신뢰도를 한 단계 높일 수 있다.

### Q45. head pose와 ArcFace는 어떤 관계인가요?

head pose는 자세 검증, ArcFace는 얼굴 특징 추출이다. 즉 서로 대체 관계가 아니라 보완 관계다.

## 4. 아키텍처 / 운영 관련 질문

### Q46. 왜 FE, BE, AI를 분리했나요?

각자 책임이 다르기 때문이다.

- FE: 촬영 UX
- BE: 인증과 비즈니스 로직
- AI: 추론

이렇게 나누면 모델 교체, 장애 추적, 배포 책임이 분리된다.

### Q47. AI 서버가 죽으면 서비스는 어떻게 되나요?

해당 기능은 영향을 받는다. 다만 백엔드는 `AI_TIMEOUT`, `OCR_UNAVAILABLE` 같은 상태를 명확히 사용자 오류로 바꿔 전달하고, 문제 원인도 AI 레이어로 좁힐 수 있다.

### Q48. 현재 재시도나 timeout 전략이 있나요?

있다. ArcFace/head pose 추론은 timeout과 retry/backoff 개념을 갖고 있다. 즉 일시 장애에 대해 바로 실패만 하지는 않도록 설계돼 있다.

### Q49. AI 기능을 운영 환경에서 더 안정화하려면 뭐가 필요하나요?

- 모델 warm-up
- health/readiness 점검
- inference latency 모니터링
- OCR/face 성공률 모니터링
- container restart 정책
- 실데이터 기반 threshold 튜닝

### Q50. 이 프로젝트 AI 파트의 다음 기술 개선 방향은 무엇인가요?

가장 현실적인 다음 단계는 다음과 같다.

- OCR 카드 영역 검출 강화
- 주민등록증 이름 추출 후처리 고도화
- stronger anti-spoofing 도입
- ArcFace threshold 실측 기반 재조정
- GPU 또는 추론 최적화 검토
- 개인정보 보호 정책 문서화 강화

## 발표 팁

발표에서 기술 질문이 들어오면 아래 원칙으로 답하면 안정적이다.

1. 모델 이름보다 역할을 먼저 설명한다.
2. `왜 이 기술을 썼는지`를 서비스 요구사항과 연결한다.
3. 현재 한계는 숨기지 않는다.
